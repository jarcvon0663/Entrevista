🧩 Test Design Techniques
⚠️
This is the topic that surprises people most: a Test Lead who cannot name and apply basic techniques loses credibility fast. Learn the five black-box techniques and be ready to solve a small example on the spot.
📚 The Big Picture
Must know

"What test design techniques do you know and when do you use each?"

"Test design techniques are systematic ways to derive test cases so we get good coverage with fewer tests. The main black-box ones are equivalence partitioning, boundary value analysis, decision tables, state transition testing and use case testing, plus pairwise testing for combinations. There are also experience-based techniques like error guessing and exploratory testing, and white-box techniques such as statement and branch coverage."

TechniqueUse it when…Core idea
Equivalence Partitioning (EP)Inputs have ranges or groupsSplit inputs into groups that behave the same; test one value per group
Boundary Value Analysis (BVA)Inputs have numeric/limit edgesTest at and around the edges, where defects concentrate
Decision TableSeveral conditions combine into outcomesList every combination of conditions and the expected action
State TransitionBehavior depends on current state/historyTest valid and invalid moves between states
Pairwise (combinatorial)Many parameters × many valuesCover every pair of values with far fewer tests
Error Guessing / ExploratoryExperience, time pressure, gaps in specsUse knowledge of typical failures; explore with a charter
↔️ EP + BVA
Worked example

"A field accepts ages from 18 to 65. Which test values do you pick?"

"With equivalence partitioning I get three partitions: below 18 is invalid, 18 to 65 is valid, and above 65 is invalid. I test one representative from each. With boundary value analysis I test the edges: 17, 18, 19, 64, 65 and 66. EP reduces the number of tests; BVA targets the edges where off-by-one bugs live."

🧮 Decision Table
Worked example

"Show me how you would test a discount rule with several conditions."

"I would build a decision table: each column is one combination of conditions with its expected action, so no combination is forgotten. Every column becomes at least one test case."

Rule: members get 5%. Orders over $100 get 10%. Members with orders over $100 get 15%.

Worked example

"How do you test something that behaves differently depending on its status?"

"I model the states and the allowed transitions, then test every valid transition and also try the invalid ones to confirm they are rejected. An order is a good example."

🔗 Pairwise Testing
Combinatorial

"When would you use pairwise testing?"

"When there are many parameters with several values each and testing every combination is impractical. Most defects are triggered by one or two parameters interacting, so pairwise covers every pair of values with far fewer tests. For example, 3 browsers × 3 operating systems × 2 languages is 18 combinations, but pairwise covers all pairs in about 9 tests. Tools like PICT or AllPairs generate the sets."

🗂️ Testing Types: Functional vs. Non-Functional
⚖️ The Core Difference
Must know

"What is the difference between functional and non-functional testing?"

"Functional testing checks what the system does: features and business rules against the requirements. Non-functional testing checks how well it does it: performance, security, usability, reliability, compatibility and so on. A login that accepts valid credentials is functional; a login that responds in under 2 seconds with 1,000 users at once is non-functional."

🧪 Smoke, Sanity, Regression, Retest
Often confused

"What is the difference between smoke, sanity, regression and retesting?"

"Smoke testing is a quick, broad check that the build is stable enough to test further. Sanity testing is a narrow check that a specific fix or change works. Regression testing verifies that existing features still work after a change. Retesting, or confirmation testing, re-runs the exact test that failed to confirm the defect is fixed."

TypeScopeWhenGoal
SmokeBroad and shallow, critical pathsNew build deployedIs the build testable?
SanityNarrow and deep, one areaAfter a small fix/changeDoes this change work?
RegressionWide, existing featuresAfter any changeDid we break anything?
RetestThe failed test cases onlyAfter a defect fixIs the bug really fixed?
📦 Levels, Box Approaches
Know the vocabulary

"What are the test levels, and what are black-box, white-box and gray-box testing?"

"The four classic test levels are unit, integration, system and acceptance testing. Black-box testing checks behavior without looking at the code, white-box testing uses knowledge of the internal structure to design tests, and gray-box testing mixes both, for example API tests that also check the database."

  • Unit: one function/class, written by developers
  • Integration: modules or services working together (APIs, databases)
  • System: the whole application end to end against requirements
  • Acceptance (UAT): business/users confirm it meets their needs
📝 Test Documentation
🆚 Test Case vs. Test Scenario
Classic question

"What is the difference between a test case and a test scenario?"

"A test scenario is a high-level statement of what to test, for example "verify the login functionality". A test case is a detailed set of steps with data, preconditions and expected results that describes how to test it. One scenario normally produces many test cases."

📋 Plan vs. Strategy
Documents you own

"Which test documents does a Test Lead own, and what is the difference between a test strategy and a test plan?"

"The test strategy is a high-level, long-lived document that defines the general approach to testing for the organization or product. The test plan is project or release specific: scope, schedule, resources, environments, risks, and entry and exit criteria. Around them sit test cases and suites, the traceability matrix, defect reports and the test summary report."

DocumentPurpose
Test strategyOverall approach, levels, types, tools, standards (changes rarely)
Test planWhat, when, who and how for one project/release
Test cases / suitesDetailed executable checks, grouped for execution
Traceability matrix (RTM)Maps requirements ↔ test cases ↔ defects to prove coverage
Defect reportEvidence and details of a failure
Test summary reportResults, metrics, open risks, go/no-go input at the end
🐞 A Good Defect Report
Often asked

"What goes in a good defect report, and what is the difference between severity and priority?"

"A good report has a clear title, environment and build, steps to reproduce, expected versus actual result, and evidence such as screenshots, logs or video. Severity is the technical impact of the defect; priority is how soon the business wants it fixed. They can differ: a typo in the company logo is low severity but high priority, while a crash in a rarely used admin report is high severity but may be low priority."

📄 Requirements Documentation
ℹ️
Names and formats vary between companies. Give the textbook definition, then say how it is used in your team.
📚 SRS vs. PRD vs. BRD
Must know

"What are SRS, PRD and BRD, and how do they differ?"

"The BRD, Business Requirements Document, explains why the project exists: business goals, stakeholders and expected benefits. The PRD, Product Requirements Document, explains what the product should do from the user point of view: features, user stories and priorities. The SRS, Software Requirements Specification, is the most technical: it details exactly how the system must behave, with functional and non-functional requirements, interfaces and constraints."

DocumentAnswersTypically owned byContainsDetail
BRDWhy?Business analyst / business stakeholdersObjectives, scope, stakeholders, benefits, success criteriaHigh level
PRDWhat?Product manager / ownerFeatures, user stories, user flows, priorities, acceptance criteriaMedium
SRSHow must it behave?Business/system analyst, architectsFunctional and non-functional requirements, interfaces, constraints, dataVery detailed

Typical flow: BRD → PRD → SRS, from business need to precise system behavior.

🧰 Using Them as a Test Lead
Practical value

"How do you use requirement documents in testing?"

"I review them for testability before development starts: looking for ambiguity, gaps and contradictions. Then I derive test scenarios and cases from them and link each one to a requirement in a traceability matrix, so I can prove coverage and see the impact of changes. In agile teams the same role is played by user stories with acceptance criteria."

  • Functional requirements → functional test cases
  • Non-functional requirements (performance, security…) → non-functional tests
  • Ask: is it clear, measurable, testable, complete, consistent?

⏳ Test Estimation
📐 Common Techniques
Must know

"What test estimation techniques do you know?"

"The ones I use most are work breakdown structure, three-point estimation, and in agile teams planning poker with story points. I also use historical data from similar projects, expert judgment, and Wideband Delphi when I want independent estimates from several people."

TechniqueHow it worksBest for
Work Breakdown Structure (WBS)Split the work into small tasks, estimate each, add upWell-understood scope
Three-point (PERT)Optimistic, most likely, pessimistic → weighted averageUncertain tasks
Planning poker / story pointsTeam votes on relative size using Fibonacci-like cardsAgile sprints
Wideband DelphiExperts estimate anonymously in rounds until they convergeLarge or risky work
Historical / analogousReuse actuals from similar past projectsRepeating projects
Percentage of dev effortTesting ≈ a ratio of development effort (rule of thumb)Early, rough estimates
Test/Function Point AnalysisSize the application, convert to effortFormal contracts
🔢 Three-Point Estimate
Worked example

"How do you calculate a three-point estimate?"

"Estimate = (Optimistic + 4 × Most likely + Pessimistic) / 6. If regression testing is 4 days at best, 6 days most likely and 14 days at worst, the estimate is (4 + 24 + 14) / 6 = 7 days. The spread, (P − O) / 6, which is about 1.7 days, tells me how uncertain it is."

PERT formula
E  = (O + 4M + P) / 6      = (4 + 4*6 + 14) / 6 = 7 days
SD = (P - O) / 6           = (14 - 4) / 6       ~ 1.7 days
🧭 Estimating with Incomplete Info
Lead-level

"How do you estimate testing when requirements are incomplete?"

"I break the work down as far as the information allows, use historical data from similar features, and write down explicit assumptions and risks. I give a range instead of a single number, add a buffer for defects, retesting and environment issues, and commit to re-estimating when requirements are clarified. I also ask questions early, because every unknown is a risk to the estimate."

  • Factors: scope, complexity, risk, team skills, environments, test data, automation, regression size
  • Include test design, execution, retesting, reporting, meetings and environment setup
  • Communicate assumptions and update the estimate as facts change
📊 Testing Metrics
✅ Pass / Fail Rate
Must know

"What is the pass rate and how do you calculate it?"

"Pass rate is the percentage of executed test cases that passed: passed divided by executed, times 100. Fail rate is the same with failed tests. I always state the denominator, because some teams divide by total planned tests."

Example: 250 planned · 170 passed · 20 failed · 10 blocked · 50 not run

📈 Other Key Metrics
Know 4–5

"Which other QA metrics do you use?"

"Beyond pass rate, I look at defect density, defect leakage, test coverage, automation coverage and defect age. They answer different questions: how buggy is it, how many escaped to production, and how much did we actually test."

MetricFormula / meaningExample
Defect densityDefects ÷ size (KLOC, module or story points)30 defects in 15 KLOC = 2 per KLOC
Defect leakageProduction defects ÷ (testing + production defects) × 1005 ÷ (45 + 5) = 10%
Defect removal efficiencyDefects found before release ÷ total defects × 10045 ÷ 50 = 90%
Requirement coverageRequirements with tests ÷ total requirements × 10090 / 100 = 90%
Automation coverageAutomated cases ÷ total cases × 100300 / 600 = 50%
Defect age / reopen rateHow long defects stay open / how many come backQuality of fixes and triage
🎤 Reporting to Stakeholders
Lead-level

"Which metrics do you report to stakeholders, and what are the pitfalls?"

"I report a small set: execution progress, pass rate, open defects by severity, defect leakage and coverage of high-risk areas, always with a trend and a recommendation. The pitfall is relying on one number: a 98% pass rate means little if the failing 2% is the checkout. And I never use bug counts to rank testers, because metrics drive behavior."

🔌 API Testing
🔢 Status Code Groups
Must know

"What are the HTTP status code groups, and which common codes should a tester know?"

"There are five groups: 1xx informational, 2xx success, 3xx redirection, 4xx client errors and 5xx server errors. In practice I check 200 for a successful read, 201 for a created resource, 204 for success without a body, 400 for invalid input, 401 when the user is not authenticated, 403 when they are authenticated but not allowed, 404 for a missing resource, 409 for a conflict, 429 for rate limiting, and 500 or 503 for server problems."

GroupMeaningCommon codes
1xxInformational100 Continue, 101 Switching Protocols

3xxRedirection301 Moved Permanently · 302 Found · 304 Not Modified
4xxClient error (the request is wrong)400 Bad Request · 401 Unauthorized · 403 Forbidden · 404 Not Found · 405 Method Not Allowed · 409 Conflict · 415 Unsupported Media Type · 422 Unprocessable Entity · 429 Too Many Requests
5xxServer error (the server failed)500 Internal Server Error · 502 Bad Gateway · 503 Service Unavailable · 504 Gateway Timeout
💡
401 vs 403: 401 = "I don't know who you are" (missing/invalid credentials). 403 = "I know who you are, but you are not allowed."
🔗 Base URL vs. Resource URL
Must know

"What is the difference between a base URL and a resource URL?"

"The base URL is the common root of the API: protocol, host and usually the version, like https://api.shopdemo.com/v2. A resource URL, or endpoint, is the base URL plus the path that identifies a specific resource, like /orders/1024. Query parameters after the question mark filter or shape the response and are not part of the resource identity."

Anatomy of a request URL
https://api.shopdemo.com/v2/orders/1024/items?status=shipped&limit=10
\________ base URL _______/\ resource path _/\____ query params ____/
  • Collection: /orders · Single resource: /orders/1024 · Sub-resource: /orders/1024/items
  • Path parameter identifies the resource (1024); query parameter filters/sorts/paginates (?limit=10)
  • Changing the base URL switches environments (dev / staging / prod) without touching the resource paths
🔧 HTTP Methods
Must know

"What are the main HTTP methods and which ones are idempotent?"

"GET reads, POST creates, PUT replaces a resource, PATCH updates part of it, and DELETE removes it. GET, PUT and DELETE are idempotent, meaning repeating the same request leaves the server in the same state. POST is not, because sending it twice can create two resources."

✅ What to Validate
Checklist

"What do you validate when testing an API?"

"I validate the status code, the response body (fields, data types and schema), the headers such as Content-Type, and the response time. Then I test negative cases like invalid input, missing fields and wrong authentication, and authorization rules such as 401 versus 403. Finally I confirm data actually persisted, for example with a GET after a POST, and I check pagination, filtering and rate limits."

  • Authentication types: API key, Basic, Bearer token (JWT), OAuth 2.0
  • Request parts: method, URL, headers, query/path params, body (JSON)
  • Tools: Postman/Newman, REST Assured, curl

🧭 What Happens When You Type a URL?
Web basics

"What happens when you type a URL in the browser?"

"The browser resolves the domain name to an IP address through DNS, opens a connection (with TLS for HTTPS), sends an HTTP request, and receives a response. It then parses the HTML into the DOM, applies the CSS, runs the JavaScript, loads extra resources like images and API calls, and renders the page."

📱 Mobile Testing: Device Selection
🎯 Selection Criteria
Must know

"How do you choose which devices to test on?"

"I start with data, not guesses: analytics from the real app (or market data for a new app) show which devices and OS versions our users actually have. Then I choose a set that covers the main OS versions, a range of screen sizes and form factors, different manufacturers (especially on Android, because of fragmentation), and low-end, mid-range and flagship performance tiers. I add devices for required hardware such as biometrics, camera, NFC or GPS, and I adjust for business priorities and past defects."

  • Usage: top devices and OS versions in analytics (Firebase/GA), target market and region
  • OS coverage: latest, previous versions, and the minimum supported
  • Screen: size, resolution, notch/foldable, tablet vs. phone
  • Manufacturer/skin: Samsung, Xiaomi, Google Pixel, Apple…
  • Hardware tier: RAM/CPU (low-end devices expose performance issues)
  • Features: biometrics, camera, NFC, sensors, connectivity
  • Risk: devices with past defects, key customers, contract requirements
🗃️ Device Matrix
Practical

"What does a device matrix look like?"

"I group devices into tiers. Tier 1 is must-test on every release, Tier 2 on major releases or regression cycles, and Tier 3 is covered by cloud devices or smoke checks."

TierExample coverageRun
1Latest iPhone on latest iOS · Popular Samsung flagship on latest AndroidEvery release
2Older/small iPhone on minimum iOS · Mid-range Android from another manufacturer · One tabletMajor releases
3Low-end Android (2–3 GB RAM) · Foldable · Older Android versionsSmoke / cloud farm

Refresh the matrix every quarter using updated analytics.

📲 Real Devices vs. Emulators
Know the trade-offs

"When do you use real devices, emulators/simulators, or a cloud device farm?"

"Emulators and simulators are fast and cheap for early development and quick checks. Real devices are needed for performance, battery, sensors, push notifications and final validation. Cloud device farms like BrowserStack, Sauce Labs, AWS Device Farm or Firebase Test Lab give broad coverage without owning every device."

  • Mobile-specific checks: interruptions (calls, notifications), network changes and offline mode, permissions, orientation, gestures, install/update/uninstall, battery and memory
⚙️ CI/CD: Jobs and Pipelines
🆚 Job vs. Pipeline
Must know

"What is the difference between a job and a pipeline?"

"A pipeline is the complete automated workflow that runs when something triggers it, like a push, a pull request or a schedule. A job is a single unit of work inside that pipeline, such as running unit tests, linting or building the app. Jobs are grouped into stages: stages run in order, and jobs inside the same stage can run in parallel. Think of the pipeline as the assembly line and each job as one station."

🔁 CI vs. CD
Know the terms

"What are continuous integration, continuous delivery and continuous deployment?"

"Continuous integration means merging code frequently and automatically building and testing every change. Continuous delivery means every change that passes is ready to be released, but a person approves the release. Continuous deployment goes one step further and releases automatically to production with no manual approval."

🧪 QA in the Pipeline
Lead-level

"Where does QA fit in a CI/CD pipeline?"

"I use the pipeline as a safety net: quick checks first, slower ones later, and a failed stage stops the release. Typical order is static analysis and linting, unit tests, build, integration and API tests, deploy to staging, smoke and end-to-end tests, then performance and security scans, with quality gates between stages."

  • Quality gate: rule that blocks promotion (e.g. no critical defects, coverage ≥ X%)
  • Fail fast: cheap tests run first; run independent jobs in parallel
  • Artifacts and reports: test results, screenshots and logs saved for every run
  • Flaky tests: quarantine and fix them, otherwise trust in the pipeline disappears

🛠️ Practical Scenarios
Show you use it

"Give me a real example of how you use the terminal in testing."

"When a test fails in CI I read the logs from the terminal, filter them with grep, reproduce an API call with curl, and re-run only the failing test from the command line. I also use pipes and redirection to save results, and I check exit codes, because that is how CI decides if a step passed."

Everyday examples
cd ~/projects/shop-tests                    # go to the project folder
ls -la                                      # list files, including hidden ones
tail -f logs/app.log | grep ERROR           # follow the log live, show only errors
grep -rn "NullPointerException" logs/       # search text recursively, with line numbers
curl -i https://api.example.com/v1/health   # call an API, print status and headers
npm test                                    # run the test suite (or: mvn test / pytest)
npm test > results.txt                      # save the output to a file
echo $?                                     # exit code of last command: 0 = success
  • | pipe: send one command output to another · > overwrite file · >> append to file
  • Exit code 0 = success, non-zero = failure; CI jobs fail on non-zero
  • Mobile: adb devices lists Android devices, adb logcat shows device logs
  • Containers: docker ps lists running containers, docker logs <name> shows their logs
🧭 Leadership Refresher
💪
Leadership is usually your strength, so keep these answers sharp, concrete and measurable. Use STAR (Situation, Task, Action, Result) with real numbers.
🗺️ Test Strategy
Lead-level

"How do you build a test strategy for a new product?"

"I start from the business goals and the main risks. Then I define the scope, test levels and types, what to automate versus run manually, environments and test data, tools, entry and exit criteria, metrics, and roles. I review it with product and engineering and revisit it as the product evolves."

⚖️ Prioritizing Under Pressure
Lead-level

"The release is in two days and you cannot test everything. What do you do?"

"I apply risk-based testing: rank features by business impact and likelihood of failure, test the critical paths and recently changed areas first, run the automated regression, and be transparent about what is not covered. I report the residual risk so stakeholders make an informed go/no-go decision."

🤝 Conflicts
Lead-level

"Developers disagree with you about a defect's severity. How do you handle it?"

"I bring evidence: reproduction steps, impact on users and business, and frequency. I align on shared severity definitions, and if we still disagree, I escalate to the product owner, who decides based on business priority. The goal is the product's quality, not winning the argument."

🌱 Mentoring
Lead-level

"How do you develop your team and measure their performance?"

"I set clear goals per person, give regular feedback and one-to-ones, pair juniors with seniors, run test-case reviews and knowledge sessions, and encourage certifications. I measure outcomes like quality of defects found, coverage, automation contributions and ownership, never raw bug counts."

⚡ Quick-Fire Round
ℹ️
Short answers you should be able to give in under 15 seconds. Use Practice mode and answer out loud.
What do 4xx and 5xx mean?

4xx: the client sent a bad request. 5xx: the server failed.

401 vs 403?

401: not authenticated. 403: authenticated but not allowed.

Base URL vs. resource URL?

Base URL is the API root (host + version); resource URL adds the path to a specific resource, like /orders/1024.

Job vs. pipeline?

A pipeline is the whole automated workflow; a job is one task inside it (inside a stage).

Test case vs. test scenario?

Scenario = what to test (high level). Test case = how to test it (steps, data, expected result).

BVA values for a field accepting 18–65?

17, 18, 19, 64, 65, 66.

Pass rate formula?

Passed ÷ executed × 100 (state your denominator).

Smoke vs. sanity?

Smoke: broad, shallow, is the build stable? Sanity: narrow, does this specific fix/change work?

SRS, PRD, BRD in one line each?

BRD: why (business goals). PRD: what (product features). SRS: exactly how the system must behave.

Three-point estimate formula?

(Optimistic + 4 × Most likely + Pessimistic) ÷ 6.

Functional vs. non-functional?

Functional: what the system does. Non-functional: how well it does it (performance, security, usability…).

Command to follow a log live?

tail -f app.log (add | grep ERROR to filter).

How do you pick mobile devices?

Start from real-user analytics, then cover OS versions, screen sizes, manufacturers, hardware tiers, features and risk.

Defect leakage formula?

Production defects ÷ (testing + production defects) × 100.

💡 Interview Tips & Best Practices
✅ Do's
  • Answer theory with Define → Differentiate → Example
  • Back leadership stories with numbers: leakage, coverage, cycle time
  • If you don't know, say what you do know and how you would find out; never stay silent
  • Use the exact terms: scenario vs. case, job vs. pipeline, 401 vs. 403
  • Ask clarifying questions before solving a technique exercise
  • Show you are still hands-on: tools, commands, real examples
❌ Don'ts
  • Don't answer a technical question with a leadership story
  • Don't assume that being a lead excuses weak fundamentals
  • Don't say "we" for everything; clarify what you personally did
  • Don't invent knowledge; say you would verify it
  • Don't blame previous teams or developers
  • Don't quote metrics without knowing the formula
🎯 Strong Closing Statements
Make an Impact

Use these to wrap up an answer or the interview:

  • "In my last team we reduced defect leakage from X% to Y% by introducing risk-based regression and quality gates in the pipeline."
  • "I like to keep my fundamentals sharp: test design techniques, estimation and metrics are what make a lead credible with the team."
  • "I can walk you through how I would set up the test strategy and device matrix for your product."
  • "I focus on delivering quality that the business can measure, while growing the people on my team."
